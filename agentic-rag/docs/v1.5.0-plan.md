## Objetivo v1.5.0

Pipeline continuo:

```
source (S3 / dir) → loader → chunker → quarantine (SEC-21)
                                          ↓ pass
                                     embedder → pgvector upsert
                                          ↓
                                     jobs table (DynamoDB)
```

Cierre explícito:
- **SEC-21** — validación con cuarentena, con razón del rechazo
  trazable.
- **RF-09** (parcial) — `metadata.source` se persiste en el chunk
  para que el grounding check (SEC-20) y futuras ACL (v2.0) lo
  consuman.
- **RNF-04** (parcial) — el job queda registrado con `attempts`,
  `last_error` y `processed_at`.

## Decisiones arquitectónicas

### Localización del código — *propuesta*

- Módulo `mcp-server/src/ingestion/`.
- Razón: mcp-server ya tiene cliente pgvector y acceso a
  DynamoDB (Floci). Evita un contenedor nuevo, IAM, healthcheck.
- Trade-off: el batch corre en el mismo proceso que el serving.
  v2.0 lo separa a `ingestion-service/`.
- Confirmar al arrancar. Alternativa: nuevo contenedor desde día
  uno (más limpio, más caro de orquestar).

### Trigger model (dev) — *propuesta*

- CLI: `npm run ingest -- <path>` (carga inmediata de un doc).
- Watcher: chokidar sobre `/data/ingestion/` (volumen en
  compose). Cualquier `.md`/`.txt` que aparezca entra al
  pipeline.
- S3 real (Floci o AWS): v1.5.x. Para v1.5.0 basta con el
  directorio + CLI; suficiente para probar el pipeline end-to-end.

### Formatos v1.5.0

- Markdown (`.md`) — extractor regex sobre headings.
- Texto plano (`.txt`) — chunker por párrafos.
- PDF, DOCX, HTML → v1.5.x (dependencias adicionales, no
  necesarias para validar la mecánica del pipeline).

### Quarantine stage (SEC-21)

Reglas v1.5.0 (cada una con id estable):
- `length_too_large` — doc > 500 KB.
- `length_too_small` — doc < 100 B (probablemente ruido).
- `pattern:<id>` — mismas regex del input guard SEC-18 aplicadas
  al cuerpo completo del doc. Un documento que intenta inyectar
  instrucciones al agente debería caer aquí.
- `encoding_suspicious` — control chars > 5% del contenido, o
  secuencias base64 largas en markdown.
- `mime_mismatch` — extensión declarada vs content sniff
  (text vs binary vs vacío).

Rechazo → estado `quarantined` en DynamoDB con `reason` poblado.
El doc NO entra a pgvector. El operador lo revisa y decide
re-procesar o descartar (CLI v1.5.x: `npm run ingest:release
<job_id>`).

## Estructura de módulos

```
mcp-server/src/ingestion/
├── types.ts          # IngestionJob, ChunkRecord, QuarantineReason
├── loader.ts         # MD/TXT extraction + metadata
├── chunker.ts        # ~500 tokens con overlap 50, respeta headings
├── quarantine.ts     # SEC-21 reglas
├── embedder.ts       # Ollama nomic-embed-text, retry + backoff
├── writer.ts         # pgvector upsert idempotente (ON CONFLICT)

├── watcher.ts        # chokidar filesystem watcher
├── cli.ts            # npm run ingest [<path>]
└── __tests__/
    ├── loader.test.ts
    ├── chunker.test.ts
    ├── quarantine.test.ts
    ├── jobs.test.ts
    └── e2e.test.ts   # CLI → pgvector (sin Ollama real)
```

## Open questions (resolver al arrancar nueva sesión)

1. **Floci S3 vs local dir**: ¿Floci S3 surface es suficiente o
   saltamos a local dir + chokidar para v1.5.0? (Recomendación:
   local dir + chokidar; S3 eventos en v1.5.x.)
2. **Chunk size**: ¿fijo 500 chars o token-aware con un tokenizer
   local? (Recomendación: fijo 500 chars para v1.5.0; token-aware
   cuando llegue el eval set dorado.)
3. **Embeddings retry**: ¿cuántos intentos y qué backoff? Default
   propuesto: 3 intentos, exponencial 1s/4s/16s.
4. **Concurrencia**: ¿1 job a la vez o pool? Default propuesto:
   serial (más simple, evita rate-limit en Ollama local).
5. **Lifecycle del archivo en `/data/ingestion/`**: ¿borrar tras
   éxito, mover a `/data/processed/`, o dejar? Default propuesto:
   dejar; el operador decide. v1.5.x añade `--remove-on-success`.

## Out of scope

- PDF / DOCX / HTML parsing.
- Floci S3 events / AWS Lambda triggers.
- Real AWS S3 + IAM roles (toca H-07 directamente).
- Bedrock Guardrails (SEC-22 layer 2).
- ACL por documento (RF-09 completo).
- Multi-tenant quarantine (un bucket por cliente).
- Streaming ingestion (todo v1.5.0 es por documento completo).
